## 一分钟介绍

下面是讲述结构，先用自己的话说，不要求背诵：

> 我做了一个 AI 辅助开发的 HTTP 巡检学习项目，叫巡小站。它可以管理多个目标，手动或定时检查，保存每次检查结果，并把同一目标连续失败合并成故障事件，恢复后记录首次发现恢复的时间。
>
> 我在 Windows 可控服务上亲手做了正常、停服务、恢复的演练，又使用 Docker Compose 运行项目，验证容器重建后的数据保留，并将 SQLite 快照导出到 Windows、恢复成新文件后校验。
>
> 项目目前是可信本机环境下的单进程工具，没有鉴权和通知，也没有生产高可用验证。代码实现和排障有 AI 辅助；我负责提出要求、反馈问题、亲手操作验收，并解释关键行为。

只保留自己能够解释、能够复现的内容，不把 AI 生成的实现等同于完全独立编写。

## 三分钟展示顺序

1. 打开离线演示页，首先指出“全部为模拟数据”，它不是实时监控、也不是实际应用界面的截图。
2. 选择目标 A，点红色失败点：解释失败耗时；指出两条连续失败合并为同一个事件，恢复后事件结束。
3. 切到目标 B：解释暂停期间状态未知，旧结果仍在，暂停不等于网站恢复。
4. 回到 README 的架构图：从手动/定时检查讲到 SQLite，再讲命名卷与导出备份。
5. 打开真实阶段验收记录：网络演练、重建、备份各说一条实际结果和一个限制。

展示真实运行实例时先确认 Docker 状态，不为了展示而访问未经授权的网站或修改已有目标。

## 需要能解释的五个问题

- 名称可以重复，为什么操作目标用编号？编号稳定且唯一，删除后不复用，避免旧页面命中新目标。
- 连续失败三次为何不是三次故障？三条检查历史可以属于同一段未恢复事件；恢复后再失败才建立新事件。
- 容器中的 127.0.0.1 是谁？它是该容器自己；访问 Windows 宿主服务使用本环境的 host.docker.internal。
- 删除容器后记录为什么还在？运行库挂载命名数据卷；未持久化的容器可写层会随删除丢失。
- Git、数据卷、备份分别解决什么？Git 管代码；卷让数据跨容器保留；独立导出的备份用于恢复到某个快照状态。
