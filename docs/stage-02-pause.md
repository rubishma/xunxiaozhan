# 第二阶段第二小步：暂停与恢复巡检

## 目的与规则

主动暂停检查不代表网站发生故障，也不证明网站正常。
当前只有手动检查；之后定时任务也应遵守同一暂停规则。

- PATCH /api/target/state 接收 JSON，例如 {"paused": true}。
- 暂停状态存入 SQLite，重启后保留。
- 暂停时 POST /api/check 返回 409，不发出目标 HTTP 请求。
- 恢复只允许后续检查，本身不请求目标，也不自动判断为正常。
- 检查执行中不接受暂停，需等待本次检查完成后重试。
- 暂停时仍可修改名称和网址；保存配置保持原有暂停状态。

## 数据升级

新版数据库增加 paused 列，0 表示允许检查，1 表示暂停。
启动时检查旧表结构，仅在缺列时执行 ALTER TABLE 添加该列。
已有名称和网址不被覆盖；后续启动不会重置暂停状态。
增量升级与备份是不同的操作，本轮并未自动备份运行数据库。

## 验证

12 项自动测试通过，包含以下新增及扩展场景：

- 统计本机目标收到的真实请求数：暂停及恢复操作不增加请求数；
  暂停期间直接请求检查接口同样不会访问目标。
- 暂停后重新执行应用启动流程，暂停状态仍保留。
- 恢复后手动检查，目标才收到一个请求。
- 旧版表升级保留名称与网址，重复启动不重置数据。
- 检查中请求暂停被拒绝，暂停状态不改变。
- 暂停接口拒绝字符串、数字等不符合布尔类型的输入。

测试只使用临时数据库与本机测试服务，未修改运行数据库。

## 学习目标与岗位能力

- 区分管理状态（暂停）和观测结果（正常或异常）。
- 理解页面限制与后端校验各自的作用。
- 理解程序升级时保留已有数据的重要性。

这些对应监控配置管理、维护期间暂停检查、接口排障与数据升级验证。
