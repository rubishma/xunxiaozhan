# 多目标管理第一小步：添加、列表与选择

## 目的

从“固定操作一个目标”变为“按编号操作选中的目标”。
本轮保留已有数据并增加目标；删除与历史入库仍未实现。

## 请求流程

页面添加目标 → POST /api/targets → 校验并查重 → SQLite 分配编号并保存。
页面选择目标 → 在配置区显示对应名称、网址与暂停状态。
点击检查 → POST /api/targets/{id}/check → 后端按 id 查询目标 → 请求该网址。
结果包含 target_id，页面按编号存放和展示，不混用不同目标的结果。

名称可以相同，编号才是稳定的记录标识。
相同网址经基本规范化后拒绝重复添加；不会尝试判断两个不同网址是否最终重定向到同一网站。
保存配置、添加、暂停和恢复操作都不会主动请求目标网站。

## 数据与并发

旧 targets 表中的名称、网址、编号和暂停状态保持不变。
仅全新数据库预置演示目标；已有空表不会在每次启动时重新插入演示数据。
创建时在一个写事务中执行查重与插入，避免并发添加重复网址。
每个目标拥有自己的锁：检查 A 时不会把 B 的检查也挡住。
仍仅支持单个服务进程。

## 验证情况

17 项自动测试通过，新增关注点包括：
- 新增不发出目标请求，配置与列表在重新启动应用后保留。
- 同名目标用不同编号区分，检查、修改和暂停不会影响其他编号。
- 并发添加同一网址只成功一次，重复编辑不会覆盖原配置。
- 不存在的编号返回 404，不会误操作第一个目标。
- 同目标重叠检查被拒绝，不同目标可以独立完成检查。
- 已有空列表不会被启动逻辑强行填充。

## 学习与岗位能力

- 使用唯一编号准确定位资源，避免误操作同名目标。
- 区分巡小站接口状态码与目标网站检查结果。
- 通过对照目标验证操作影响范围。
- 理解“本页暂存结果”与“数据库历史记录”的区别。

## 独立操作

在现有目标之外添加“本机404测试”，网址为：
http://127.0.0.1:8765/missing-demo-page

分别检查首页和该路径，预期得到 200 与 404。
切换后核对编号和实际网址；暂停第二个目标，确认第一个仍可检查。
再尝试重复添加，并重启后确认两条配置仍在。
