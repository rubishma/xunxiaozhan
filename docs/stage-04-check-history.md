# 检查历史与重启保留

## 目的与范围

把每次检查结果写入数据库，支持刷新和重启后查看最近结果与最近 20 条记录。
本轮新增 checks 表与历史查询接口，修改页面和测试，不增加依赖。
既有目标、配置、暂停状态与编号保持不变；旧版页面内存结果无法补回。
暂不做定时任务、曲线、故障事件、分页或自动清理。

## 一次检查的流程

点击检查 → 按目标编号取得锁 → 读取配置并判断暂停 → HTTPX 请求目标。
记录当时的名称、网址、HTTP 状态码、耗时、UTC 检查开始时间和错误原因。
正常、HTTP 错误、连接失败和超时均写入 checks，每次真正完成的检查一条。
写入提交成功 → 接口返回结果 → 页面读取历史并展示。
暂停或重复执行被拒绝时没有进行检查，因此不增加历史。
若请求完成但数据库写入失败，接口返回 503 和“检查已执行，但历史保存失败”，日志保留具体原因。
这时没有已保存的新记录，恢复数据库后下一次检查仍可进行。
进程被强制结束可能留下未记录的在途检查，当前版本没有任务补偿机制。

## 数据关系

- targets：当前目标配置。
- checks：检查记录，通过 target_id 关联目标；同时保留名称和网址快照。
- 修改配置不覆盖旧记录，便于知道那次实际检查的是哪个网址。
- 暂停保留历史，恢复仅允许后续检查。
- 删除目标通过外键级联删除其历史；每个数据库连接都启用外键，删除失败时事务整体回滚。
- 新目标不会复用旧编号，也不会继承已删除历史。

历史按写入编号倒序，使用目标编号与记录编号的索引；接口最多返回 20 条。
更早记录仍留在数据库，长期使用需要后续加入保留策略。
UTC 入库，页面统一转换成北京时间；耗时使用独立的计时器计算。
API：GET /api/targets/{id}/history；无记录为 []，目标不存在为 404。

## 页面行为

选择目标读取历史，最新一条显示在最近结果区域，历史列表显示当时配置。
加载中、加载失败、没有记录分别显示，不会把读取失败说成从未检查。
列表只缓存已经读取的最近状态；重新选中目标会重新查询，不自动轮询。
更改网址后，旧结果仍展示并提示网址已变更；需要重新检查当前网址。
快速切换目标时通过请求序号忽略过期响应，避免 A 的结果覆盖 B。
删除确认框明确说明会删除全部历史。

## 验证记录

2026-09-30：26 项自动测试通过，全部使用临时数据库和本机可控服务。
新增重点：
- 正常、异常、恢复记录分别保存；配置快照与时间在重新启动应用后保持。
- 连接失败和超时保存为空状态码、实际耗时和错误原因。
- 不同目标历史隔离，最近 20 条限制不删除更早记录。
- 暂停、重复检查被拒绝时不增加记录。
- 写入失败返回明确错误，已有历史不丢失，锁释放后下一次可正常检查。
- 删除目标及历史原子执行，模拟删除失败能回滚，不影响其他目标。
页面 JavaScript 语法检查通过；使用模拟 DOM 和可控响应顺序验证了过期响应隔离、读取错误、空历史及空选择。
这些逻辑验证不等于浏览器布局验收，手机显示尚未验收。

## 学习与岗位能力

- 学会：持久化、目标与历史关联、保留当时配置、区分检查失败与保存失败。
- 岗位能力：通过时间顺序复盘故障，保留排障记录，核对重启前后的数据。
- 应独立完成：正常检查一次，关闭被监控服务检查一次，恢复服务再检查一次，然后重启巡小站核对历史。
- 面试问题：页面刷新不丢历史是否就说明数据库有备份？为什么？
- 本轮理解问题：服务停止时没有收到 HTTP 响应，为什么仍然应该保存一条检查记录？
